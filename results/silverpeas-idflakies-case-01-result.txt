Matched detector orders:
Original: A -> B

The same seeded original-order file was used under both protocols.

CLEAN PROTOCOL

Original A -> B:
- order starts with deployments absent
- A runs with deployments absent
- A creates deployments
- B runs with deployments present
- B passes

Reverse B -> A:
- new JVM begins with deployments present from the preceding execution
- clean protocol reset removes deployments before the test order
- B runs with deployments absent
- B errors
- A then recreates deployments

iDFlakies:
- detected testInstall as order-dependent
- intended result: PASS
- revealed reverse result: ERROR
- detection list contains 1 test

REUSED PROTOCOL

Original A -> B:
- order starts with deployments absent
- A creates deployments
- B runs with deployments present
- B passes

Reverse B -> A:
- new JVM begins with deployments present from the preceding execution
- reused protocol does not remove deployments
- B runs with deployments present
- B passes
- A follows

iDFlakies:
- detected 0 order-dependent tests
- detection list is empty

RESULT

Under identical iDFlakies test-order executions, resetting cross-execution
persistent filesystem state exposes the Silverpeas order dependency, while
reusing that state masks the order-sensitive outcome.

Clean state:
  A -> B : B PASS
  B -> A : B ERROR
  iDFlakies detects B

Reused state:
  A -> B : B PASS
  B -> A : B PASS
  iDFlakies does not detect B

The causal difference is the deployments directory that persists across
separate detector JVM executions.

This establishes that, for this real IDoFT case, cross-execution persistent
filesystem state can change whether iDFlakies reports an order-dependent test.

This result demonstrates consequence for this case; it does not by itself
establish prevalence across IDoFT.
